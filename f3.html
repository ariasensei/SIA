Lesson 3

Performance Optimization

Making a game system faster, smoother, and more efficient without sacrificing correctness.

Core concept

What Is Performance Optimization?

Performance optimization improves how efficiently a system uses CPU, memory, storage, network, and database resources.

Example: A game launcher should load quickly, show player progress without delay, and save scores reliably.

Key metrics

How Do We Measure Performance?

Response Time

Time needed to answer a user request.

Frame Rate (FPS)

How smoothly the game renders frames.

Memory Usage

RAM consumed while running.

Throughput

Number of requests or tasks handled over time.

Bottlenecks

Why Do Systems Become Slow?

  • Large images, textures, audio, or game assets.
  • Inefficient code and unnecessary repeated operations.
  • Slow database queries or missing indexes.
  • Too many API calls or unstable network connections.
  • Insufficient server resources during high traffic.
Optimization strategies

Optimize the Game and Front End

  • Compress textures and optimize models and assets.
  • Load resources only when needed (lazy loading).
  • Reduce unnecessary rendering and background processes.
  • Cache reusable files and data where appropriate.

Goal: faster loading and smoother gameplay.

Optimization strategies

Optimize Back End and Database

  • Use efficient SQL queries and appropriate indexes.
  • Return only the data needed by the dashboard.
  • Use pagination for large leaderboards.
  • Minimize redundant API requests; use safe caching.

Example: Fetch the top 10 leaderboard entries instead of every player record.

Engineering principle

Measure Before You Optimize

Monitor → Identify bottleneck → Improve → Test again

  • Use browser developer tools and server logs.
  • Compare loading times and resource use.
  • Check that the changes do not break functionality.

Optimization should be evidence-based, not guesswork.

Lesson 4

Deployment and
Distribution

Moving an integrated game system from development into a usable release.

Definitions

Deployment vs. Distribution

Deployment

Installing, configuring, and running the system in its target environment.

Distribution

Delivering the released application to users through a website, installer, or platform.

A deployed web game can be distributed by sharing its public URL.

Environments

Where Does the System Run?

  • Development: programmers build and debug locally.
  • Testing / Staging: the team validates a release before publishing.
  • Production: real users access the live system.

XAMPP on a developer's laptop is a local development setup—not automatically a public deployment.

Release workflow

Typical Deployment Process

Build → Test → Configure → Deploy → Verify → Monitor

  • Prepare application files and required dependencies.
  • Configure server, database, and environment settings.
  • Run functional and security checks.
  • Verify login, gameplay, score saving, and leaderboard.
Architecture

Example: Web-Based Game Launcher

Player's Browser

↓ HTTPS requests

Web / Application Server

↓ Database queries

Database: Accounts, Scores, Progress

The game files and application services must be accessible in the deployed environment.

Distribution channels

How Do Players Receive the Game?

  • Web: public URL accessed in a browser.
  • Desktop: downloadable installer or game launcher.
  • Mobile: application package or app store.
  • Game platforms: storefront or approved distribution service.
Reliability and security

What Must Be Ready Before Release?

  • Secure authentication and role-based permissions.
  • HTTPS and protected configuration secrets.
  • Database backups and a rollback plan.
  • Monitoring, error logging, and version control.
  • Testing on intended devices and browsers.
Important distinction

Publishing Is Not the Finish Line

After deployment, developers must monitor performance, fix defects, update dependencies, and protect player data.

Example: If score saving fails after release, logs and monitoring help the team locate and correct the issue.
