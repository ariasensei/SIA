Lesson 1 • Cloud

What a cloud service provides

  • Remote computing resources and managed services accessed through a network.
  • Examples include server hosting, databases, object storage, authentication, and monitoring.
  • Providers operate infrastructure, while developers still configure access and application behavior.
  • Network delays, outages, quotas, and cost become architecture concerns.

Lesson 1 • Decisions

Benefits and tradeoffs

Why teams use cloud services

Managed infrastructure can reduce maintenance work and support access across devices. Capacity can grow when configured appropriately.

What teams must evaluate

Usage costs, provider limits, internet dependence, regional availability, migration effort, and responsibility for player data.

Lesson 1 • APIs

API, endpoint, and SDK

API

A defined interface for interacting with a system. Example: submit a run and receive a run ID.

Endpoint

A specific network address and operation, such as GET /api/v1/leaderboard.

SDK

A library that wraps service calls and platform details. Example: a game-engine client library for a cloud service.

Lesson 1 • HTTP

An HTTP request has a contract

POST /api/v1/runs HTTP/1.1
Authorization: Bearer <player-access-token>
Content-Type: application/json
Idempotency-Key: run-7f31

{"match_id":"m-42","completion_event":"e-8"}

Method identifies the action. Path identifies the resource. Headers carry metadata. The body carries structured data.

Lesson 1 • Security

Authentication and authorization

Authentication: Who are you?

A valid session or access token identifies the player.

Authorization: What may you do?

The backend checks whether this player owns the requested save or may perform the action.

Changing a URL from /players/p-017/save to /players/p-018/save must never grant access to another player’s data.

Lesson 1 • Security

Trust boundaries and secrets

  • Use HTTPS to protect data in transit.
  • Keep privileged API keys and database credentials in backend configuration.
  • Verify identity, ownership, and permitted actions on the trusted side.
  • Validate rewards using authoritative game records and game rules.
  • Apply least privilege and avoid logging access tokens or personal data.
Lesson 1 • Workflow

Planning a cloud integration

  • Define the player feature and its expected behavior.
  • Choose the service and read its authentication, schema, limits, and error documentation.
  • Map local fields to the external data contract.
  • Build a backend adapter and configure separate development credentials.
  • Implement timeouts, failure states, and observability.
  • Test the boundary in staging before release.
Lesson 1 • Code reading

Reading a leaderboard safely

async function loadLeaderboard() {
  const response = await fetch("/api/v1/leaderboard", {
    signal: AbortSignal.timeout(5000)
  });
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  const data = await response.json();
  if (!Array.isArray(data.entries)) {
    throw new Error("Unexpected leaderboard format");
  }
  return data.entries;
}

Caller catches failures and shows “Leaderboard unavailable. Try again.”

Lesson 1 • Reliability

Timeouts, retries, and duplicate actions

Timeout

Stop waiting after a chosen limit. A timeout does not prove that the server rejected or never processed the request.

Retry

Repeat selected temporary failures with bounded exponential backoff and jitter. Honor provider guidance such as Retry-After.

Idempotency

Reuse the same operation ID for retries. The backend stores and returns the original result instead of granting rewards again.

Lesson 1 • Synchronization

Cloud saves and conflicts

  • Device A loads save version 12. Device B also loads version 12.
  • Device A uploads progress and creates version 13.
  • Device B submits older state based on version 12.
  • The backend detects a version mismatch and returns a conflict.
  • The game asks the player to choose or applies a documented merge rule.

Lesson 2 • Foundations

Testing and debugging

Testing

Execute planned checks to discover differences between expected and actual behavior.

Debugging

Investigate evidence to locate a fault, correct its cause, and verify the repair.

Example: a test finds duplicate coins. Debugging traces the duplicate to a retried reward request.

Lesson 2 • Strategy

Testing approaches and test doubles

Incremental integration

Connect a few components at a time. Failures are easier to localize than after a large final merge.

Stub or mock

A stub supplies controlled responses. A mock can verify interactions. Both simulate a dependency.

Real dependency check

Use a sandbox or staging service to verify actual authentication, serialization, and persistence.

Lesson 2 • Coverage

Beyond the happy path

Boundary values

Check zero, maximum allowed values, empty fields, and just-outside-range values.

Concurrent requests

Two reward requests arrive together. Uniqueness and transaction rules must prevent duplication.

Delayed and reordered events

An older save arrives after a newer save. Version checks must protect progress.

Compatibility

An older client calls a newer API. Required fields and error formats must remain compatible.

Lesson 2 • Method

A repeatable debugging process

  • Reproduce the failure with exact inputs and environment.
  • State expected and actual behavior.
  • Follow one request through client, network, API, and data store.
  • Form a hypothesis and change one relevant factor.
  • Fix the root cause and rerun the failing test.
  • Add a regression check and verify related workflows.
Lesson 2 • Case study

Case 1: “Saved” but progress disappears

Observed behavior

Game shows “Saved.” After restart, the player returns to the earlier level.

Evidence to collect

HTTP status, response body, save owner, stored version, transaction outcome, and reload request.

  • Hypothesis: the UI displays success before the API confirms the write.
  • Fix: show confirmation only after successful persistence. Handle errors and pending states.
  • Regression: force a write failure and verify the game never reports a confirmed cloud save.
Lesson 2 • Case study

Case 2: duplicate reward after reconnect

  • Server commits a 50-coin reward, but the response never reaches the client.
  • Client retries and server grants another 50 coins.
  • Trace both requests using the same logical operation ID.
  • Enforce uniqueness for that operation and apply reward changes transactionally.
  • Test sequential retries and concurrent duplicate requests.
Lesson 2 • Case study

Case 3: works in an API client, fails in browser

Possible evidence

The browser console reports a CORS error or the preflight request fails.

Investigation

Compare origin, allowed methods, allowed headers, and credential settings with the server’s policy.

Configure an explicit allowed origin and correct preflight handling. CORS controls browser access and does not replace authentication.

Lesson 2 • Regression

Verification after a fix

  • Rerun the original failure using the same inputs.
  • Check nearby behaviors such as valid saves and conflict handling.
  • Automate important repeatable boundary tests.
  • Reset test data so repeated runs stay independent.
  • Review logs for unexpected errors and unintended side effects.
Lesson 2 • Class discussion

Debugging challenge: frozen leaderboard

  • A player finishes a run. POST /runs returns 201.
  • The database shows the accepted result. GET /leaderboard returns 200.
  • The UI still shows the old ranking for five minutes.
  • Identify two possible causes and the evidence that distinguishes them.
