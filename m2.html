II–III. Introduction and Simple Definition

What is an architectural pattern?

Software architecture is the overall structure of a software system and the way its major parts communicate with each other. An architectural pattern is a commonly used way of organizing that structure.

Think about a house

A bungalow, apartment, townhouse, and two-story home can all provide shelter, but each organizes rooms and connections differently. Software systems also need a structure that fits their purpose.

Think about a game

An online multiplayer game might organize communication using clients, a game server, and a database. That reusable organization is called Client-Server Architecture.

Simple definition

Architectural Pattern = a reusable solution for organizing the major parts of a software system and defining how those parts communicate.

PLAYER ↓ GAME CLIENT ↓ GAME SERVER ↓ DATABASE CLIENT-SERVER ARCHITECTURE

V–VI. Patterns and Why They Matter

Architectural pattern vs. design pattern

Architectural Pattern

Deals with the overall structure of the system: its major parts and their communication.

CLIENT ↓ SERVER ↓ DATABASE

Easy memory tip: Architectural Pattern = big picture.

Design Pattern

Deals with a smaller programming or design problem inside the larger system.

ENEMY DIES ↓ OBSERVER ├── Score ├── Quest └── UI

Easy memory tip: Design Pattern = smaller solution inside the system.

Good architectural choices make systems easier to understand, maintain, test, debug, expand, and integrate.

Without planned responsibilities, changing inventory may break combat, changing UI may break saving, and changing the database may affect player features.

VIII–XV. Pattern 1

Layered Architecture

Layered Architecture divides software into different layers. Each layer has a focused responsibility and usually communicates with nearby layers instead of directly accessing everything.

┌──────────────────────────────┐ │ Presentation Layer │ ├──────────────────────────────┤ │ Business Logic │ ├──────────────────────────────┤ │ Data Access Layer │ ├──────────────────────────────┤ │ Data Storage │ └──────────────────────────────┘

Presentation Layer

Handles what players see and interact with: menus, HUD, inventory screens, settings, pause menus, and character screens.

Business Logic

Handles game rules such as calculating damage, reducing HP, checking death, validating purchases, or completing a quest.

Data Access

Loads and saves player data, inventories, leaderboards, and other stored records.

Data Storage

Contains actual information in MySQL, SQLite, JSON files, local files, or cloud databases.

PLAYER ↓ SHOP UI ↓ SHOP LOGIC ↓ INVENTORY SERVICE ↓ DATA ACCESS ↓ DATABASE

Advantages

  • Easy to understand
  • Clear responsibilities
  • Easier maintenance and testing
  • Components can change independently

Disadvantages

  • Can become rigid
  • Many layers can complicate communication
  • May add overhead for very small games

XVI–XX. Pattern 2

Client-Server Architecture

Client-Server Architecture divides a system into clients that request services and servers that provide services. It is one of the most important patterns for online and multiplayer games.

PLAYER 1 ──┐ PLAYER 2 ──┼──→ GAME SERVER ──→ DATABASE PLAYER 3 ──┘

Client

The client is the game application used by the player on a PC, phone, console, or web browser. It may handle graphics, input, UI, animation, and local gameplay processing.

Server

The server manages shared services such as player accounts, multiplayer state, matchmaking, sessions, leaderboards, authentication, and database communication.

PLAYER A ATTACKS PLAYER B ↓ ATTACK REQUEST ↓ SERVER VALIDATES ATTACK ↓ UPDATE GAME STATE ↓ PLAYER B HP = 50 ↓ SEND RESULT TO CLIENTS

Authority means deciding which information is correct. In many competitive games, the server is authoritative: it decides whether an attack really hit and whether the result is valid.

XXI–XXIV. Pattern 3

MVC: Model, View, Controller

Model

Contains data and data-related rules.

PLAYER ├── Name ├── Level ├── HP └── XP

View

Displays information to the player.

PLAYER STATUS Name: Aria Level: 10 HP: 80 / 100 XP: 500

Controller

Receives input and coordinates actions.

CLICK EQUIP ↓ CONTROLLER ↓ MODEL ↓ UPDATE VIEW

MVC is useful for game launchers, account systems, inventories, leaderboards, online game portals, administrative systems, and UI-heavy applications. It may be less suitable for the real-time gameplay loop of a small game.

XXV–XXIX. Pattern 4

Component-Based Architecture

Component-Based Architecture is extremely important in game development. Instead of creating one huge object, developers divide functionality into reusable components.

PLAYER │ ├── Transform ├── Movement ├── Health ├── Combat ├── Inventory ├── Animation └── Audio

Health Component

Manages current HP, maximum HP, damage, healing, and death.

Movement Component

Manages movement, jumping, sprinting, and movement state.

Inventory Component

Adds, removes, finds, and organizes game items.

PLAYER ────────┐ ENEMY ─────────┤ BOSS ──────────┼──→ HEALTH COMPONENT NPC ───────────┘

A chest may use Transform, Interactable, Inventory, Animation, and Audio components. An enemy may use Transform, Health, AI, Combat, Animation, and Audio. Components can be combined according to the needs of each object.

XXX–XXXIII. Pattern 5

Event-Driven Architecture

An event is something that happens in a system. In Event-Driven Architecture, systems announce events and other interested systems respond independently.

Coin collected

PLAYER COLLECTS COIN ↓ CoinCollected EVENT ↓ SCORE · AUDIO · UI +10 SOUND UPDATE

Player dies

PLAYER HP = 0 ↓ PlayerDied EVENT ↓ UI · AUDIO · SAVE · GAME MANAGER

Advantages

  • Loose coupling
  • Multiple systems can respond
  • Easy to add listeners
  • Useful for complex games

Disadvantages

  • Harder to trace actions
  • Too many events can confuse teams
  • Requires good event management

XXXIV–XLV. Patterns 6–9

More patterns for larger systems

Microservices Architecture

A platform is divided into small independent services with focused responsibilities. An online game platform may use separate Authentication, Matchmaking, Leaderboard, Payment, and Game services.

GAME PLATFORM │ ┌────┼─────┐ ↓ ↓ ↓ AUTH MATCH LEADERBOARD ↓ GAME SERVICES

Use it carefully: Microservices may help a huge online platform, but they are usually unnecessary for a small student project or offline RPG.

Repository Pattern

A Repository lets application code access data without directly depending on a database implementation. This makes it easier to replace MySQL, local files, or a cloud database later.

PLAYER SERVICE ↓ PLAYER REPOSITORY ↓ DATABASE

Pipe-and-Filter Architecture

Data passes through a series of processing stages. Each filter processes information and sends it to the next stage.

KEYBOARD INPUT ↓ INPUT FILTER ↓ MOVEMENT FILTER ↓ COLLISION FILTER ↓ ANIMATION FILTER ↓ PLAYER MOVEMENT

Peer-to-Peer Architecture

Computers communicate directly with each other rather than relying entirely on a central server. It can reduce central-server dependence but creates security, cheating, synchronization, and connection-quality concerns.

PLAYER A ←→ PLAYER B ↕ ↕ PLAYER C ←→ PLAYER D

XLVI–L. Comparison and Selection

Choose the pattern that fits the problem

Pattern Main Idea Game Use
Layered Divide a system into responsibility levels Game management systems, save systems
Client-Server Clients communicate with a central server Multiplayer games
MVC Separate Model, View, and Controller UI-heavy applications
Component-Based Build objects from reusable components Gameplay objects
Event-Driven Components respond to events Game events and notifications
Microservices Divide a large platform into services Large online platforms
Repository Separate data access from logic Save and data systems
Pipe-and-Filter Process data through stages Input and rendering pipelines
Peer-to-Peer Peers communicate directly Some multiplayer systems

Scenario A: Small offline platformer

One player, no database, no multiplayer, and ten levels.

Possible choice: Component-Based Architecture because reusable gameplay components can organize players, enemies, pickups, and level objects.

Scenario B: Online MMORPG

Thousands of players, accounts, multiplayer, database, chat, and leaderboards.

Possible choice: Client-Server + Layered + Component-Based + Event-Driven + Microservices.

LI. Game Development Case Study

Case Study: Battle Arena

Your team is creating a 5v5 multiplayer battle arena with player accounts, character selection, weapons, skills, health, matchmaking, leaderboards, database support, game UI, sound effects, and player statistics.

Communication between players?

Client-Server Architecture. A central server can validate actions and maintain shared state.

Gameplay functionality?

Component-Based Architecture. A player may have Health, Movement, Combat, Weapon, and Skill components.

What happens when a player dies?

Event-Driven Architecture. UI, Audio, Score, Respawn, and Statistics systems can react to PlayerDied.

Separate UI, logic, and data?

Layered Architecture. It provides clear responsibility boundaries between presentation, rules, services, and storage.

LXVI–LXVII. Final Challenge and Summary

Architect before you code

Before beginning a game project, do not immediately start writing detailed code. First determine the game type, target users, major systems, responsibilities, communication paths, data storage requirements, multiplayer needs, and patterns that fit the requirements.

GAME │ ├── COMPONENTS ├── EVENTS ├── CLIENT │ ↓ │ SERVER │ ↓ └──── DATA ↓ DATABASE THE BEST ARCHITECTURE IS NOT THE MOST COMPLICATED ONE. THE BEST ARCHITECTURE APPROPRIATELY SOLVES THE PROJECT'S PROBLEMS.

Final takeaway

Architectural patterns are tools, not rules that developers must blindly follow. Choose structures that make the game easier to build, maintain, test, integrate, scale, and improve.
