Part I · Introduction to Software Architecture

2. What is software architecture?

Software architecture is the overall structure or blueprint of a software system. It is similar to a house blueprint: before construction begins, an architect decides where rooms, electrical systems, plumbing, connections, and pathways belong.

Before developers build a large software system, they decide what major components it will have, what each component will do, how components communicate, where data is stored, how users interact, how external systems connect, and how the system can grow later.

Simple definition

Software Architecture = the high-level structure of a software system and the way its major parts work together.

3. Why architecture matters

Growth reveals architecture problems

At first, a game feels simple

  • 1 player
  • 3 enemies
  • 1 map
  • 5 weapons

It may seem reasonable to put almost everything into one large script.

Then the game grows

  • 50 enemies and 20 maps
  • Multiplayer and online accounts
  • Inventory, quests, and customization
  • Save/load, leaderboards, and purchases

Changing one feature can suddenly break three others. That is an architecture problem.

Maintainability

Make the system easier to modify and repair.

Scalability

Allow the game to grow without a complete rewrite.

Reusability

Reuse components in different parts of the game.

Testability

Test individual parts independently.

Performance

Identify systems consuming too many resources.

Teamwork

Let different developers work on different components.

Part II · Architecture vs. Design vs. Implementation

5–7. Three related but different concepts

Architecture

Answers: “What are the major parts of the system and how do they communicate?”

PLAYER ↓ GAME UI ↓ GAME LOGIC ↓ DATABASE

Design

Answers: “How will each component work internally?”

INVENTORY ├── AddItem() ├── RemoveItem() ├── FindItem() └── CalculateWeight()

Implementation

Means actually writing the code that makes the design work.

public void AddItem(Item item) { inventory.Add(item); }

Remember: Architecture = what major parts exist. Design = how parts are organized internally. Implementation = how the code is written.

Part III · Software System Components

8–10. Components, responsibilities, and modularity

A component is a major part of a software system with a specific responsibility. A game may include Player, Combat, Inventory, Quest, Enemy AI, Save, Audio, UI, and Database systems.

Bad architecture: one giant script

A single Player.cs script handles movement, combat, inventory, saving, audio, dialogue, quests, and UI. This becomes difficult to maintain.

Better architecture: separate responsibilities

PLAYER CONTROLLER │ ├── Movement System ├── Combat System ├── Inventory System ├── Quest System └── Save System

Modularity means dividing a system into smaller independent modules. If an Inventory System needs replacement, a modular game can swap the old module for a new one without rewriting the entire game.

Part IV · Common Architectural Patterns

11–19. Patterns for organizing software

12. Layered Architecture

Layered Architecture divides software into levels. The UI should not directly manipulate the database; requests should flow through game logic and data access layers.

┌─────────────────────────────┐ │ Presentation · Game UI / HUD│ ├─────────────────────────────┤ │ Business Logic · Game Rules │ ├─────────────────────────────┤ │ Data Access · Save / Load │ ├─────────────────────────────┤ │ Data Storage · Files / MySQL│ └─────────────────────────────┘

14. Client-Server Architecture

The client is the player’s software, such as a PC or mobile game. A server provides shared services such as multiplayer state, databases, accounts, cloud saves, and leaderboards.

INTERNET │ ┌─────▼─────┐ │ SERVER │ └─────┬─────┘ │ ┌───────┼────────┐ ↓ ↓ ↓ Player Player Player Client Client Client

In a multiplayer battle game, a client sends an attack request to the server. The server validates the action, updates the target’s HP, and sends the result back. This reduces cheating and keeps game state synchronized.

16. MVC Architecture

MVC means Model – View – Controller. The Model handles data and rules, the View handles what the user sees, and the Controller receives input and coordinates the system.

PLAYER │ ▼ ┌──────────┐ │Controller│ └────┬─────┘ │ ┌────┴────┐ ▼ ▼ Model View Data UI

If a player clicks “Save Game,” the Controller receives the request, the Model provides current game data, and the View displays “Game Saved!” MVC is useful for launchers, leaderboards, inventories, account systems, and web-based game tools.

18. Component-Based Architecture

Game objects are made from reusable components rather than one giant object. A player can have Transform, Movement, Health, Combat, Inventory, Audio, and Animation components.

PLAYER │ ├── Transform ├── Movement ├── Health ├── Combat ├── Inventory ├── Audio └── Animation

The Health Component handles current HP, maximum HP, damage, healing, and death. Enemies and bosses can reuse the same Health Component while adding their own AI or special attack components.

Part V · Event-Driven Architecture

20–22. Let systems respond to events

An event is something that happens in a system: a player dies, an enemy is defeated, an item is collected, a quest is completed, a button is clicked, or the game is paused.

Enemy defeated

ENEMY DIES ↓ EnemyDied Event ↓ Score · Quest · Audio · UI Systems respond independently

Coin collected

PLAYER TOUCHES COIN ↓ CoinCollected Event ↓ Score +10 · Play SFX · Update UI

The enemy does not need to directly control every other system. It announces “EnemyDied!” and interested systems decide how to respond.

Part VI–VII · Game Architecture and Engines

23–28. Major systems inside a game

GAME │ ┌─────────────┼─────────────┐ ↓ ↓ ↓ INPUT GAMEPLAY UI │ ┌────────┼────────┐ ↓ ↓ ↓ Combat AI Quest │ ↓ DATA ┌───────┴───────┐ ↓ ↓ Save Database

Input System

Handles keyboard, mouse, controller, and touchscreen input.

Player System

Handles movement, health, attributes, equipment, and player state.

Combat System

Handles attacks, damage, weapons, skills, hit detection, and critical hits.

Enemy AI

Handles enemy movement, attacks, NPC behavior, and decision-making.

Inventory and Quest

Manage items, equipment, objectives, rewards, progress, and completion.

Save, Audio, and UI

Store progress, play music/SFX, and present menus, HUDs, maps, and trackers.

A game engine is a platform that provides rendering, physics, animation, audio, input, scene management, scripting, and asset management. Examples include Unity, Unreal Engine, and Godot.

GAME │ ┌──────────┼──────────┐ ↓ ↓ ↓ Graphics Physics Audio │ │ │ └──────────┼──────────┘ ↓ Game Logic ↓ Game Objects ↓ Assets

Part VIII · Architectural Quality

29–32. Coupling, cohesion, scalability, maintainability

Coupling

Coupling describes how strongly components depend on each other. High coupling makes changes risky because everything depends on everything else. Prefer lower coupling when practical.

Cohesion

Cohesion describes how closely related responsibilities are inside a component. An Inventory System should add, remove, find, and count items—not play music or control enemy AI.

Scalability

Scalability is the ability to handle growth, such as moving from 100 to 10,000 players without rebuilding the entire system.

Maintainability

Maintainability is how easily developers can fix bugs, add features, replace components, and improve performance. A good architecture lets a new weapon be added mainly through the Weapon System.

Part IX–XII · RPG and Integration Examples

33–39. Architecture of a simple RPG

A simple RPG may contain a player, enemies, weapons, inventory, quests, NPCs, levels, save/load, and UI.

RPG GAME │ ┌─────────────────┼──────────────────┐ ↓ ↓ ↓ UI GAMEPLAY DATA │ │ ┌──────────┼──────────┐ │ ↓ ↓ ↓ │ Combat AI Quest │ │ │ │ │ └──────────┼──────────┘ │ ↓ │ Inventory │ ↓ │ └──────── Save System ──────────┘ ↓ Database

Scenario: Player dies

Health System detects HP = 0 ↓ PlayerDied Event ↓ Animation → death animation Audio → death sound UI → game over screen Save → current state Game Manager → stop gameplay

System integration

System integration connects different software components so they can work together. A game can connect with a game engine, database, authentication service, payment service, online server, and APIs.

GAME → API → SERVER → DATABASE

An architecture diagram is a visual representation of major components and their communication. It helps developers, teachers, clients, and team members understand a system quickly.

Activity 1: Analyze the architecture

Individual activity · 2D RPG

Scenario

You are developing a 2D RPG containing Player, Enemies, NPCs, Inventory, Weapons, Quests, Health System, Game UI, and Save System.

Tasks

  1. What is the purpose of software architecture?
  2. Identify at least five components of the game.
  3. Give the responsibility of each component.
  4. Which component should manage player health, inventory, quests, and UI?
  5. Why should the Inventory System not be responsible for enemy AI?
  6. Draw a simple architecture diagram.
  7. Identify one possible dependency between two components.

Sample guidance: Components can include Player, Health, Inventory, Quest, Enemy AI, UI, Combat, and Save Systems. Each should have one responsibility. The Inventory System should not manage AI because these concerns are unrelated and would reduce cohesion.

Part XIX · Mini Case Study

The Impossible Game

Imagine a team creates a game using one giant Game.cs file containing Player, Enemy, Weapons, Inventory, Quests, Audio, UI, Saving, Database, Multiplayer, and AI. After six months, the game has 30,000 lines of code in one file.

One developer changes the Weapon System. Suddenly inventory stops working, enemy AI crashes, save data fails, and the UI displays incorrect information.

The problem is not simply too many features. The problem is that the architecture does not separate responsibilities properly.

GAME │ ├── Player System ├── Combat System ├── Enemy AI ├── Inventory ├── Quest ├── UI ├── Audio ├── Save └── Multiplayer

Part XX · End-of-Lesson Takeaway

Build systems that can survive growth and change

Game Development students are not only learning to create characters, environments, scripts, animations, and gameplay. They are also learning to build software systems that can grow, accept new features, support more players, and remain maintainable.

GOOD SOFTWARE ARCHITECTURE = Clear Components + Clear Responsibilities + Good Communication + Low Unnecessary Dependencies + High Cohesion + Maintainability + Scalability

Suggested resources for further study: Microsoft Architecture Center, Unity Learn, Unreal Engine Documentation, Godot Documentation, Object Management Group UML resources, and NIST systems engineering references.
