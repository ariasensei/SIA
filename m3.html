II–V. Introduction · Definition · Engine vs. Game

What is a game engine?

Software architecture is the overall structure of a system. In game development, the key question is: how is the game engine itself structured? When Play is pressed, many systems begin working together.

INPUT ↓ GAME LOGIC ↓ PHYSICS → ANIMATION → RENDERING → SCREEN ↓ AUDIO

Simple definition

A game engine is a software framework or platform that provides reusable tools and systems for creating, running, and managing games.

Game Engine

The engine provides technology and tools: rendering, physics, audio, input, scene systems, scripting, AI tools, assets, networking, UI, and debugging tools.

Game

The game is the actual product built with the engine: characters, levels, weapons, enemies, quests, rules, and player experiences.

GAME ENGINE ↓ PHYSICS · AUDIO · RENDERING ↓ GAME ↓ CHARACTERS · LEVELS · WEAPONS · ENEMIES · QUESTS

Examples of game engines include Unity, Unreal Engine, Godot, and GameMaker. Their terminology differs, but most need input, rendering, physics, audio, game logic, assets, scenes, and animation.

VII–XLI. Architecture and Core Subsystems

A game engine is an integrated system

GAME ENGINE │ ├── GAME LOOP ── GAME LOGIC ── Physics · AI · Animation · Audio · Rendering ├── RESOURCE MANAGER └── EDITOR ↓ OUTPUT → SCREEN

A subsystem is a major functional part of a larger system. Each subsystem has a focused responsibility, but none works in isolation.

Rendering System

Processes models, textures, lights, shadows, cameras, materials, and effects to generate images. A 2D renderer works with sprites and 2D cameras; a 3D renderer works with meshes, lighting, materials, shadows, and 3D animation.

Physics System

Simulates gravity, collision, friction, movement, forces, velocity, and acceleration. Colliders detect intersections; rigid bodies participate in physical simulation.

Input System

Receives keyboard, mouse, controller, touch, and VR commands. Input abstraction maps devices to actions, such as Spacebar or Controller A becoming “Jump.”

Audio System

Handles music, sound effects, voice, environmental sound, and positional 3D audio. Background music is usually 2D; a nearby enemy growl can depend on direction and distance.

Animation System

Manages idle, walk, run, jump, attack, and death states. Animation state machines transition between visual states such as Idle → Run → Attack → Idle.

AI System

Controls enemies, NPCs, companions, and animals. It can detect players, decide to patrol/chase/attack, and use pathfinding such as A* to avoid obstacles.

Game Logic & Scripting

Controls rules such as XP, damage, quests, doors, rewards, and game-over states. Scripts use the engine API instead of rebuilding physics or rendering from scratch.

Scene Management

Organizes menus, levels, battle areas, and worlds. A scene graph can show parent-child relationships between environment, player, camera, weapons, enemies, and UI.

Asset Management

Finds, loads, unloads, organizes, and tracks dependencies for models, textures, materials, sounds, maps, animations, and UI resources.

Entity + Components

PLAYER ENTITY ├── Transform ├── Renderer ├── Physics ├── Health ├── Movement └── Inventory

Component-based design assembles objects from reusable functionality.

Entity-Component-System

ENTITY → identifies object COMPONENT → stores data SYSTEM → processes matching data

ECS separates entities, components, and systems and can improve large-scale object processing.

XLII–XLVIII. Game Loop and Timing

The repeating heartbeat of a game

The game loop is the repeating process that updates the game and produces frames while the game is running.

START ↓ READ INPUT ↓ UPDATE GAME ↓ PHYSICS → AI → ANIMATION → AUDIO ↓ RENDER ↓ NEXT FRAME → REPEAT

Frames, FPS, and Delta Time

A frame is one displayed image. FPS means Frames Per Second: 60 FPS produces about 60 frames each second. Delta time is the elapsed time since the previous frame, helping movement remain consistent: Movement = Speed × Delta Time.

Update vs. Render

Update changes game state: positions, enemy behavior, HP, or quests. Render draws the current state: models, environment, effects, and UI. Physics often uses a consistent fixed update step for stability.

L–LXVIII. Editor, Runtime, Build, Hardware and Performance

From editor to screen

GAME ENGINE │ ├── EDITOR → Scene Editor · Asset Manager · Inspector └── RUNTIME → Input · Game Loop · Scripts ↓ Physics · AI · Animation · Audio ↓ Rendering → GPU → SCREEN

Editor, Runtime, and Build Pipeline

The editor is used to place objects, import assets, configure lighting, create animation, write scripts, and test. The runtime executes the game. A build compiles scripts, processes assets, packages files, and prepares the game for Windows, Android, consoles, or other platforms.

CPU and GPU

The CPU handles general-purpose work such as game logic, AI, input, physics calculations, and resource management. The GPU specializes in parallel graphics work such as rendering, shaders, lighting, and visual effects.

What happens when Play is pressed?

The runtime starts, a scene loads, objects and assets load, systems initialize, then the game loop begins: Input → Update → Physics → AI → Animation → Render → Repeat.

Performance Architecture

Architecture affects performance. Improve heavy games through object pooling, culling, level of detail (LOD), efficient data structures, multithreading, spatial partitioning, and ECS approaches.

OBJECT POOLING → reuse bullets instead of recreating them CULLING → skip objects outside the camera view LOD → use lower-detail models farther away MULTITHREADING → perform suitable work concurrently

LXIX–LXXXII. Individual and Group Activities

Apply the architecture

Individual Activity 1 · Trace the Action

The player presses Spacebar to jump.

Trace the process from Input to Screen. Identify the Input System, Player Controller, Physics System, Animation System, and Rendering System. Then explain what may happen if the Physics System fails.

Spacebar → Input System → “Jump” action → Player Controller → Physics System changes velocity → gravity and collision update player position → Animation System selects jump animation → Rendering System draws the updated player → Screen. If physics fails, the player may not leave the ground, collide correctly, or fall predictably.
Individual Activity 2 · Identify the Subsystem

Identify the primary subsystem for: pressing W, gravity affecting a box, a metallic sword appearance, enemy searching, gunshot audio, walking-to-running animation, 3D environment display, loading textures/models, saving progress, and repeatedly updating the game.

1. Input System · 2. Physics System · 3. Rendering / Material System · 4. AI System · 5. Audio System · 6. Animation System · 7. Rendering System · 8. Asset Management · 9. Save / Serialization System · 10. Game Loop.
Individual Activity 3 · Build a Mini Engine

Create a diagram for an engine containing Input, Rendering, Physics, Audio, Animation, Game Logic, and Asset Manager. Explain each subsystem, identify which communicates with the GPU, which communicates with input devices, which loads assets, and how the systems communicate.

Group Activity: Design a Game Engine

In groups of 4–5, design a simple engine supporting 2D and 3D games. Include Input, Rendering, Physics, Audio, Animation, Scene Management, Asset Management, Game Loop, Scripting, and UI. Trace one action such as jump, shoot, attack, open a door, or collect an item. Identify likely bottlenecks when the game runs at 20 FPS.

LXXX–LXXXVI. Case Study · Review · Key Takeaways

The Laggy Game

A 3D open-world game with 500 enemies, high-resolution textures, a large map, dynamic lighting, physics objects, music, and particle effects runs at 15 FPS. Do not automatically blame graphics. Investigate rendering, physics, AI, memory, asset loading, animation, audio, and game logic.

Too many visible objects?
Culling can avoid rendering objects outside the view.
Objects far away?
LOD can use simpler models at distance.
500 enemy decisions?
AI may need improved scheduling, culling, or data-oriented processing.
Repeated bullets?
Object pooling reuses objects.
Huge textures?
They can pressure memory, loading, and GPU resources.
Why investigate broadly?
CPU, GPU, RAM, storage, and system integration all affect performance.
KEY TAKEAWAYS 1. Engines are platforms for creating and running games. 2. Games are built on top of engines. 3. Engines contain integrated subsystems. 4. Rendering creates visuals; physics simulates behavior. 5. Input receives commands; audio manages sound. 6. Animation manages visual movement. 7. The game loop updates and renders repeatedly. 8. Subsystems must communicate to make a game work.

Final message for students

Do not think of a game engine as a magic tool that creates a game for you. It is a large integrated software system. When a player moves, shoots, collides, hears sound, or loads a level, multiple subsystems cooperate. Understanding how they work together is the foundation of Game Engine Architecture.
